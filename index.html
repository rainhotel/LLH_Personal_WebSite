01 / CAMPUSBites · QQBOTPRIVATE SOURCE · REVIEWED

从群消息，到有证据的推荐

不是让模型自由生成店名和价格，而是先理解意图、召回真实候选，再由服务端执行硬约束并组装最终事实。模型参与判断，但不拥有业务事实。

The model does not invent shop names or prices. It interprets intent and reranks real candidates; the server enforces hard constraints and renders the final facts. The model reasons, but it does not own business truth.

服务端拥有硬约束

学校、公开可见性、店铺 ID、营业与事实字段由服务端决定；模型输出不能覆盖它们。

School scope, public visibility, shop IDs, operating state, and factual fields remain server-owned; model output cannot override them.

先过滤，再让模型排序

菜品/品类、店铺、检索词三路召回；学校、地点、店型、预算等硬过滤后，最多将 8 个真实候选交给重排。

Dish/category, shop, and retrieval-term recall feed hard filters for school, location, shop type, and budget before at most eight real candidates reach the reranker.

模型故障有安全回退

AI 不可用时回退 SEARCH_ONLY；搜索本身失败时返回固定不可用提示，不拿模型猜测冒充结果。

When AI is unavailable, the flow falls back to SEARCH_ONLY. If search itself fails, it returns a controlled unavailable response instead of guessing.

运行过程可追踪、可反馈

Redis 租约与去重保护长连接；有界队列控制并发；推荐上下文加密追加保存，并通过 requestId 关联用户反馈。

Redis leases and deduplication protect the connection; a bounded queue controls concurrency; encrypted append-only traces are linked to user feedback by requestId.

IMPLEMENTATION BASISQQBot module specification · runtime · services · tests · private repository
02 / CAMPUSBites · MEAL AGENTPRIVATE SOURCE · REVIEWED

地点不是搜索关键词

用户说“西苑附近”，Agent 不应该把“西苑”硬拼进菜品关键词。地点先被解析成受限引用，再由服务端校验当前学校范围。

When a user says “near West Campus,” the agent should not append that phrase to a dish keyword. Location becomes a scoped reference first, then the server validates it against the current school.

隔离学校边界

模型看不到数据库区域 ID；旧 ref、低置信度或跨学校 ref 都不会触发搜索。

The model never sees database location IDs. Stale, low-confidence, or cross-school references do not trigger search.

地点与菜品分离

地点约束独立于 queryText 和 dishOrCategory，并进入共享搜索缓存键。

Location constraints stay separate from queryText and dishOrCategory, and are included in the shared search cache key.

03 / XPERT · PLUGIN PLATFORMPUBLIC PR EVIDENCE

把插件能力放在正确的边界上

平台不应该为每个插件写一套特殊分支。SDK 定义稳定契约，宿主负责权限与生命周期，插件实现具体 provider 行为。

The host should not grow provider-specific branches for every plugin. The SDK defines stable contracts, the host owns permissions and lifecycle, and plugins implement provider behavior.

契约先于实现

通过 Plugin SDK 定义身份绑定、SSO Provider 与集成测试结果契约，减少宿主和插件的耦合。

Plugin SDK contracts for identity binding, SSO providers, and integration test results reduce coupling between host and plugins.

生命周期由宿主编排

通用集成更新/删除流程调用策略钩子，让插件能完成自己的资源清理与重配置。

Generic integration update/delete flows dispatch strategy hooks so plugins can handle their own cleanup and reconfiguration.

04 / WECHAT OAM · FILE PIPELINEPRIVATE SOURCE · REVIEWED

大文件不必穿过应用服务器

上传链路把文件传输与业务处理拆开：客户端直接上传对象存储，后端只负责签发、确认和调度任务。这样应用服务器不需要承接整份文件的带宽与内存压力。

The upload flow separates file transfer from business processing: the client uploads directly to object storage, while the backend signs, confirms, and schedules work. The application server does not need to carry the full file payload.

DIRECT UPLOAD → ASYNC PROCESSING
01POST /presignsigned upload URL
→
02PUT to COSclient → object storage
→
03POST /confirmverify uploaded object
→
04Async taskstore object reference
→
05GET task statuspoll progress
传输与处理解耦

文件字节由客户端直传 COS，避免经由 Spring Boot 接口中转整份文件。

File bytes go directly from the client to COS instead of being proxied through the Spring Boot application.

任务只携带引用

确认后创建异步任务，任务参数保存对象引用与元数据，前端通过 taskId 查询处理状态。

Confirmation creates an asynchronous task with object references and metadata; the frontend follows progress by taskId.
